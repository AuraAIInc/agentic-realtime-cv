**Upheld / overturned by code:**

| Code | Upheld | Overturned | Reading |
| ---- | ------ | ---------- | ------- |

| P6 (merge) | — | — | no verdict: API error dropped the escalation |

**What improved.** Same working loop as last run — queue → agent → parse →
journal → apply → chart → memory — now with the chart generated in-pipeline.
It fixed the same 2 mislabeled rows and confirmed 167 rows plus 3
interpolated runs and 1 split.

**What limited the improvement:**

1. **Recall is still the bottleneck** (§2): 3/3 sampled T2 relabels
   overturned, ~770 pass through untouched. Unchanged.
2. **The one lost verdict cost the only merge.** E9's 400 → `error` verdict
   is a silent row no-op with no retry; the visit-3/visit-4 merge from last
   run simply didn't happen. Error verdicts are also trust-gated out of
   memory (correctly), so the failure leaves almost no trace beyond the log
   line and the traceless run dir.
3. **Same two apply bugs, reproduced**: T2 same-frame cross-talk (E6/E7) and
   the last-writer `verdict` field. Order-dependence cut the other way this
   time: E12's keep matched only because E9 failed first.
4. **Two new verdicts are recorded-but-unapplied**: `drop_box_as_outlier`
   (T4 `_noop`) and `merge_neighbor` (neighbor unknown). The journal says
   more than the rows do.
5. Same external taxes: production period-id collision (11 wasted calls),
   image-server Pillow outage (16/16 zooms failed).

**Cost of the session's validation:** 517,607 tokens, $0.60, ~9.4 min for 12
escalations — ≈ 47 s, ≈ 47k tokens, ≈ $0.054 per completed escalation
(detail §7). E9's partial spend is unrecorded (no trace). Tracking cost ~1 s
and $0; memory promotion ~1.7 min (§8).

Bottom line: the safety net held — same 2 fixes, same confirmations, one
fewer merge through no fault of the pipeline's own. The run's real news is
on the memory side (§8): the trust gate and short-term memory worked as
designed on their first live session.

## 10. How to run it

Prerequisites (all from the repo root, venv active):

1. `.env` at the repo root with `MODEL_API_KEY` (Meta model API) and the
   MySQL credentials — every entry point loads it.
2. Backends up: `camera_sim` on `:8766` (or the real camera server), the
   image server (`10.0.0.165:10001`), the tracking server
   (`52.53.150.209:10002`).

```bash
python -m agent.main --view-id 3 \
  --start 2026-10-28-16-33 --end 2026-10-28-16-40 \
  --replay-db --validate --memory --plot
```

Flags: `--replay-db` streams the window from MySQL (read-only; shared DB is
never written); `--validate` starts the supervisor-agent queue;
`--memory` enables long + short-term memory; `--plot` draws the three
charts. Outputs land in `output/tracking_runs/<run>/` (gitignored) and
`output/agent_runs/<timestamp>-validation/` (one trace + evidence jpgs per
escalation). Expect ~10 min wall time and ~$0.60 in agent tokens for this
7-minute window.
