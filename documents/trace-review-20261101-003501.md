## A. Bugs and correctness risks

### A1. `images__get_image` with `box=` or `max_side=` always fails (PIL missing) — 4 wasted calls
`image_server/mcp_image_server/image_store.py:154` does `from PIL import Image`
inside `transform()`, and Pillow is not installed in the image server's
environment. Any `get_image` with a crop or resize therefore errors:
trace #15 (`max_side: 800`), #26–#28 (all three `box=crop_box` calls). The
model burned a full turn (#25–#28) plus ~1.8 s on crops that can never succeed,
then fell back to full frames.
Fix options: install Pillow in the image-server env; or make `transform()`
failure non-fatal (return the stored bytes plus a `"transform_error"` note) so
callers still get pixels. Impact beyond this run: zoomed identity checks (the
skill ladder rung 3) are impossible on stored frames right now.

### A2. Image budget is charged for failed image calls
`agent.py:_budget_refusal` reserves budget *before* execution ("parallel calls
must not overshoot"), and nothing refunds on error. In this run 4 of 10
image-returning calls returned errors (A1 + one evicted track frame) yet all
10 counted (`images_used: 10`, only 5 images saved). In pipeline tasks (budget
2–3) a couple of server errors would exhaust the budget without the model ever
seeing a pixel, forcing `send_to_human`. Recommend: keep the reservation, but
decrement when the outcome has no image / is an error.

### A3. `tracking__get_arrival_path` took 7.25 s, 6.41 s of it in `pick`
Trace #24: `steps_ms = {memory: 107, db: 458, pre_roll: 217, pick: 6410}`.
`motion.picks_by_distance` over a path built from 4,000+ rows of a stationary
period is the hotspot (likely super-linear in path length). The payoff was 2
key frames for a cat that never moved. Cap the candidate path before picking
(e.g. downsample rows first), and/or short-circuit when total travelled
distance is tiny ("cat never moved; entry + latest are enough").

### A4. `empty_before` frame was not empty
The model verified frame `2026-11-01-07-09-18-729488.jpg` (labelled
`empty_before`, 0.35 s before `entry`) and the cat is already visible. The
"last frame with no cat" lookup (`history.last_empty_frame`) disagrees with
the detector by at least one frame, so the role label teaches the model a
false premise. Either widen the gap required before calling a frame empty,
or rename the role (`just_before_entry`) so the model treats it as "check"
rather than ground truth.

### A5. Chat-loaded skills return unstripped frontmatter; task path strips it
`tasks.load_skill()` regex-strips the `---` frontmatter; `local_tools/skills.py:Skill.read()`
returns the file verbatim (trace #8 shows `---\nname: ...` in the payload). Two
inconsistent copies of the same instructions; the chat copy wastes tokens and
exposes authoring metadata. Strip in `Skill.read()` so both paths share it.

### A6. `camera__get_track_frame` buffer-eviction failure is not predictable
Trace #30: track 1's frame "has already left the buffer". The buffer spans
<1 min at full rate, and `get_status` already reports oldest/newest — but the
model cannot map `track_id → frame time` without `get_track_history` first, and
the tool description only says "often under a minute". Cheaper contract:
on eviction, return the nearest buffered frame for that track (or an
`oldest_available` hint) instead of a bare error.

## B. Token / time inefficiencies in this run

### B1. Fixed per-turn cost: 38 tool schemas + 1,622-token system prompt
Every turn re-sends 38 function definitions (incl. 4 skill tools and niche
tools like `set_schedule`) plus the folded instructions. Input floor at turn 1
was already 9,722 tokens before any tool result arrived. Pipeline tasks avoid
this via `tasks.py` tool allow-lists (10 tools for validate); free chat has no
such restriction. Biggest single lever: give chat a default tool subset (or
split tools into groups the model can unlock), and never expose `skill__*` in
chat (B4).

### B2. `get_period_detail` returns a 60-point path for a stationary cat — 1,884 tokens
Trace #23: `path` is ~60 × `{"time": ..., "x": 379.0, "y": 75.5}` for a cat
whose net displacement is 0.7 px, on top of `period`, `frames`,
`first/last/best_frame`, and full motion segments that largely duplicate
`get_current_periods` from turn 3. Options: lower default `max_points` (60 →
~20), run-length-compress repeated centres, or omit `path` when travelled
distance is below a threshold and say so. Tasks already pass `max_points: 2`
in `_period_summary` — chat callers get no such discipline from the prompt.

### B3. `get_live_status` and `get_current_periods` overlap; the model bought both
Turn 1 `get_live_status` already returned period 103063 ongoing, latest
detection, box, conf. Turn 3 `get_current_periods` cost 544 ms and 1,148
tokens, ~80% re-stating the same visit plus 10 `recently_final` periods the
answer never used. Either document a strict preference in the prompt
("live_status for *now*; current_periods only for just-ended visits"), pass
`final_limit: 0` when only the ongoing visit matters, or slim
`recently_final` entries (drop first/last frame objects by default).

### B4. Skill invoked in free chat where its preconditions don't exist (1 turn, ~850 tokens, 14 s)
`validate-cat-identity` assumes a pipeline payload (`context`, `cats`, `crop`
preloaded, strict-JSON answer). A chat user asked a free-form question; loading
the skill cost one LLM turn and the instructions were then only loosely
followed (no JSON answer, ladder rungs skipped/reordered). The skill
description says "Use for validate_detection tasks", but nothing enforces it.
Options: hide `skill__*` tools unless a task/skill mode is active; or add a
BASE_INSTRUCTIONS line that skills are pipeline-task procedures, not chat
workflows.

### B5. Tool errors caused duplicate fetches; no negative caching
`2026-11-01-07-09-19-078258.jpg` was fetched twice (failed crop, then full);
`07-35-02` failed with `max_side`, its successor frame fetched next turn. Each
image is ~120–130 KB and a full vision input. Once A1 is fixed, crops
(~384 px) should replace most full frames: the one successful crop this run
(`get_track_frame`, 174×190) carried the decisive cue (plume tail tip) at a
fraction of the vision cost. Also consider: `frame_crop()` in local tools
already fetches whole frames and crops locally for tasks — the same helper
could serve chat instead of server-side `box=`.

### B6. Exploratory calls with no downstream use
`camera__list_buffered_frames(limit=50)` (386 tokens of timestamps) and
`tracking__list_views` (696 chars) were barely used; `camera__detect` with
`yolov8s` predictably returned COCO labels (`dog`, `sports ball`, `cat_id: -1`)
— `list_models` documents `cat_classes`, but `detect`'s own description does
not warn that non-cat models cannot validate cat identity. Net: ~2 turns of
"exploring" before evidence gathering started in earnest. Prompt-level fix:
a cheap-first checklist for "find/validate a cat" (status → capture/crop →
detect with the cat model) instead of open-ended tool browsing.

### B7. Cache behaviour is erratic; uncached input is the top cost line
`cached_tokens` per turn: 0, 113, 113, 113, 12,017, 113, 11,121, 23,921,
24,561. The prefix (instructions + tool schemas + history) should be identical
turn over turn under `previous_response_id` chaining, yet most early turns got
essentially no cache discount (113 tokens) and turn 6 fell back to 113 after
turn 5 hit 12k. At $1.25 vs $0.15 per 1M, cache misses are ~8× the cached rate;
uncached input ($0.107) exceeds output cost. Worth investigating: is the
gateway's prompt cache keyed on the full request (tool list order must be
byte-stable — `hub.tools` dict order should be, but verify), and does the
cache expire between slow turns (12–25 s each, should not)? Even a stable
50% cached rate would have saved ~$0.04/run (~23%).

### B8. Output tokens grow every turn; final answer is very long
Output per turn: 231 → 442 → 613 → 846 → 1,407 → 1,953 → 1,947 → 3,036 →
3,454, while visible text per turn is one short sentence plus tool calls. The
balance is reasoning effort spent re-deriving context that grows each turn —
fewer turns (B1/B4/B6) attacks this directly. The final answer (4,511 chars)
restates nearly every tool result verbatim, partly because BASE_INSTRUCTIONS
says "mention which tools you used and the server-side elapsed_ms". For chat,
cap the default answer shape (conclusion + evidence + caveats); keep the
full audit trail in `trace.md`, which now exists for exactly that purpose.

### B9. No budgets in chat mode
Pipeline tasks get `image_budget`, `high_res_budget`, `max_steps` from
`agent.yaml`; chat runs with `image_budget=None` and `max_steps=12`
(`config.py`). This run used 9 turns / 10 image calls for a question that was
answerable in ~4 turns. Recommend chat defaults (e.g. image budget 6, a soft
turn budget with a "wrap up" nudge), so a wandering run degrades gracefully
instead of spending $0.18.

### B10. Tool-result payloads carry fields the model never uses
Examples: `camera__get_status` returns frame-buffer byte counts, websocket
queue depths, replay progress (1,376 chars); `local__get_cat_profiles`
returns `tracking_ids`, `confused_with` decoys and full cue lists for both
cats when only distinguishing cues matter at decision time. These are cheap
individually but re-billed every later turn (see header note). Slim defaults
with an opt-in `detail` parameter (profiles already have one — default it
tighter) pay compound interest.

## C. Redundant prompt / description text

1. **Three copies of the same facts.** Coordinates `[x1,y1,x2,y2]`, the image
   name format, and "pass `image_name` to `images__get_image`" each appear in
   `prompts.py` BASE, camera `INSTRUCTIONS`, tracking `INSTRUCTIONS`, and again
   in tool descriptions. The assembled system prompt is 6,488 chars before
   server notes end. Single-source them: keep mechanics in server notes/tool
   descriptions, keep BASE to behaviour + tool selection only.
2. **BASE re-describes every tool group** that the 38 tool descriptions already
   define. The group map is useful for tool *choice*, but e.g. the
   `capture_high_res` explanation appears in BASE, in camera `INSTRUCTIONS`,
   and in the tool description itself. Trim BASE's per-tool detail to one line
   per group.
3. **Tracking glossary vs BASE overlap.** "A period's cat_id is the identity to
   trust; a frame's detector_cat_id is only a label" is stated in both BASE
   and the tracking server notes, as is the final/ongoing caveat. Keep one.
4. **Skill text vs task code.** `validate-cat-identity` rung 1 (visit
   consensus, exclusion) is already implemented in `tasks.py` before the model
   is called — the model re-reads instructions for a decision code may have
   taken. The skill could start at "code has not decided this; here is what
   remains", shortening both the skill and the input.
5. **`check-trajectory` skill vs `analyze_trajectory` output.** The flag table
   in the skill duplicates flag semantics that `trajectory.analyze` could
   return as one-line explanations alongside each flag (only for flags that
   actually fired, which is shorter than the full table on every call).

## D. Skill improvement opportunities

- **validate-cat-identity:** state explicitly it is pipeline-only (see B4);
  strip frontmatter once (A5); start after the code-decided rungs (C4); add
  "if `box` width < ~60 px, skip owner photos and go straight to a sharper
  view or human" — this run showed tail-tip identity at 56 px is not
  eye-verifiable, yet the ladder spends images discovering that.
- **check-trajectory:** already the tightest skill (one contact sheet, no
  extra images). One gap: it says segments must cover the whole visit but
  gives the model no segment skeleton; returning `analysis.segments` prefilled
  would cut output tokens and malformed-JSON retries.
- **assign-activity-label:** input already includes `rules` that decide most
  context labels; the skill could instruct the model to echo
  `context_decided` verbatim instead of re-deriving (and re-billing) them.
- **manage-labels:** the only skill used interactively, yet it is unreachable
  via `skill__*` discipline in normal chat (B4 cuts both ways). If skills stay
  invocable in chat, this is the one that belongs there; gate the other three
  to task mode.
- **Missing skill:** "live cat check / detection validation" as a chat
  workflow. This run improvised one across 9 turns; a short skill (status →
  one crop → cat-model detect → answer) would encode the cheap path that
  B1/B6 ask for, instead of loading a pipeline skill that does not fit.
